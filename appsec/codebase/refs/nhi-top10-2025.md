# OWASP Non-Human Identities (NHI) Top 10 — 2025

Lazy-loaded reference for Phase 3b of `/codebase`. Category names and risk descriptions are sourced
directly from the official OWASP Non-Human Identities Top 10, 2025 edition
(`owasp.org/www-project-non-human-identities-top-10/2025/top-10-2025/`), last synced 2026-08-31.
The "Code-level checks" under each category are this skill's own translation into what's actually
verifiable from a source-code read — the same way Phase 5b translates the OWASP LLM Top 10 into
concrete grep patterns rather than restating the abstract category.

An NHI is any credentialed identity that isn't a human logging in interactively: a service account,
an API key, a CI/CD pipeline's OIDC token, a Kubernetes ServiceAccount, a bot, a webhook secret, an
IAM role assumed by a workload.

---

## NHI1:2025 — Improper Offboarding

**Risk**: Deactivated or removed services still have live, working NHIs attached — deprecated
integrations and their credentials remain accessible instead of being revoked alongside the thing
they served.

**Code-level checks**: grep for API keys/service-account references belonging to a provider,
integration, or internal service the codebase no longer actually calls (a Stripe key still read
from config for a payment flow that was removed; an IAM role still granted to a Lambda that no
longer runs; a webhook secret validated for an endpoint that returns 410/is commented out). This is
largely a **process/lifecycle question a static read can flag but not fully confirm** — note it as
"credential appears orphaned — needs live/inventory confirmation" rather than forcing a definitive
verdict from source alone.

## NHI2:2025 — Secret Leakage

**Risk**: NHI credentials (API keys, tokens, encryption keys, certificates) end up in unsanctioned
places during development — hardcoded in source, committed to a repo, sitting in a plaintext config
file, or pasted into a public channel/log.

**Code-level checks**: this is what Phase 4's `trufflehog` pass and the secrets-liveness pattern
already cover (see Phase 4 notes in `SKILL.md` and `appsec/aikido-triage/references/secrets-
playbook.md` for the opt-in liveness-probe procedure) — don't duplicate that work here, just note
the overlap.

## NHI3:2025 — Vulnerable Third-Party NHI

**Risk**: A third-party integration in the dev workflow — an IDE extension, a SaaS build tool, a
CI marketplace action — is compromised (vulnerability or malicious update) and used to steal the
credentials it was granted.

**Code-level checks**: inventory what third-party tools/extensions/actions hold credentials at all
— a CI action given `secrets: inherit` or broad `permissions:`, a SaaS integration granted an API
key with more scope than its actual function needs. Overlaps `/supply-chain`'s malicious-install-
hook and CI/CD review — cross-reference rather than duplicate; this section's job is just to flag
*which* NHIs are exposed to third-party tooling risk, `/supply-chain` proves whether a specific
tool is actually compromised.

## NHI4:2025 — Insecure Authentication

**Risk**: A service-to-service or service-to-API integration uses a deprecated, weak, or
known-attackable authentication method instead of current standards.

**Code-level checks**: grep for service-to-service auth using HTTP Basic over plaintext, static
API keys where the provider offers short-lived OAuth2 client-credentials or mTLS instead, a signing
algorithm on service tokens that's deprecated (HS256 with a weak/shared secret where asymmetric
signing is available, or `alg: none` accepted anywhere in a JWT verification path), or a webhook
that only checks a shared-secret query param instead of an HMAC signature over the payload.

## NHI5:2025 — Overprivileged NHI

**Risk**: A service account, IAM role, or API key is granted far more permission than its actual
function requires; if that identity is ever compromised, the attacker inherits the excess.

**Code-level checks**: read the actual IAM policy/role definition (not Aikido's or the cloud
console's paraphrase of it) attached to each service identity found in the codebase and compare
granted actions/resource scope against what the code that uses that identity actually does — a
Lambda that only needs to read one S3 prefix but holds `s3:*` on `Resource: "*"`, a CI token with
repo-admin when it only needs to push a tag. This is the same blast-radius reasoning
`appsec/aikido-triage/references/misconfig-playbook.md` Step 2 already uses for IAM findings — reuse
that reasoning style here rather than reinventing it.

## NHI6:2025 — Insecure Cloud Deployment Configurations

**Risk**: CI/CD systems authenticate to cloud providers with either static credentials (which risk
exposure via repos/logs/config) or OIDC (which is only as safe as its trust-policy validation — a
missing or over-broad `sub`/`aud` condition defeats the whole point of using short-lived tokens).

**Code-level checks**: this is the specific CI/CD OIDC trust case that gets its own **MANDATORY**
chain to `/cloud-identity-federation` (see CHAIN COMMITMENTS) — grep GitHub Actions/GitLab CI
workflow files for `id-token: write` / `permissions: id-token: write`, then find the corresponding
cloud-side IAM role trust policy (`token.actions.githubusercontent.com`, GitLab's or CircleCI's
OIDC issuer) and check whether the trust condition pins `sub` to a specific repo/branch/environment
or is left wildcarded (`repo:org/*:*`, no `ref:` qualifier at all). Also flag any static long-lived
cloud credential (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` as a plain CI secret) where an OIDC
role would eliminate the standing credential entirely.

## NHI7:2025 — Long-Lived Secrets

**Risk**: API keys, tokens, encryption keys, and certificates are issued with expiration dates set
far in the future or with no expiration at all — a breach of one grants indefinite access.

**Code-level checks**: for every service credential found, check whether the issuing configuration
sets an explicit, short TTL (a token-refresh/rotation call present in the code, a cert with a
< 1-year validity period configured in IaC) or whether it's a "create once, never rotate" pattern —
no refresh logic anywhere, a cert/key generation script with no expiry parameter at all, a long-
lived personal/service API key hardcoded where a session-scoped token would work.

## NHI8:2025 — Environment Isolation

**Risk**: The same NHI credential is reused across development, testing, staging, and production
instead of each environment having its own — a compromise in a lower-trust environment (dev) grants
production access.

**Code-level checks**: grep config/env-var loading across environment-specific files (`.env.dev`
vs `.env.production`, `config/staging.yml` vs `config/production.yml`, Terraform workspace
variables) for the identical credential value or the identical variable name pointing at the same
underlying secret-manager path rather than a per-environment one. A CI pipeline that injects the
same `DATABASE_URL`/`API_KEY` secret into both a staging and a production deploy job is the
canonical version of this.

## NHI9:2025 — NHI Reuse

**Risk**: A single NHI credential is shared across multiple unrelated applications, services, or
components — compromising one gives an attacker access to everything else using that same
credential, even where the systems are otherwise unrelated.

**Code-level checks**: across a monorepo or a set of related repos, grep for the same credential
variable/secret-manager reference name appearing in more than one distinct service's config — a
single "the org's Stripe key" or "the shared internal API token" imported by five different
microservices instead of each holding its own scoped credential.

## NHI10:2025 — Human Use of NHI

**Risk**: A developer or admin manually uses an automation credential (a service account, a CI
token, a bot's API key) for a task that should go through their own individual human identity —
this erases the audit trail distinguishing a person's action from automation and often carries more
privilege than the person's own account would.

**Code-level checks**: this is primarily a **process/behavioral question, not something a static
source read can confirm** — a codebase can at most surface a *suspicious signal* (a service
account's credential referenced in a personal script, a Makefile target, or a `scripts/` helper
clearly meant for ad hoc/manual invocation rather than CI). Note it explicitly as "needs
live/process confirmation" rather than rendering a source-only verdict.

## Summary: what's genuinely code-verifiable vs. process-only

| Category | Code-verifiable from source? |
|---|---|
| NHI1 Improper Offboarding | Partial — can flag orphan-looking credentials, can't confirm the service is actually gone |
| NHI2 Secret Leakage | Yes — covered by Phase 4 trufflehog + secrets-liveness, not duplicated here |
| NHI3 Vulnerable Third-Party NHI | Partial — can inventory exposure, `/supply-chain` confirms compromise |
| NHI4 Insecure Authentication | Yes |
| NHI5 Overprivileged NHI | Yes |
| NHI6 Insecure Cloud Deployment Config | Yes — this is the one with a MANDATORY chain to `/cloud-identity-federation` |
| NHI7 Long-Lived Secrets | Yes |
| NHI8 Environment Isolation | Yes |
| NHI9 NHI Reuse | Yes, when the codebase spans the affected services |
| NHI10 Human Use of NHI | No — process/behavioral, flag as a suspicious signal only |
